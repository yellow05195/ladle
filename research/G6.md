# G6 — Slot time measurement (Solana mainnet-beta)

Date of measurement: 2026-10-23 (12:26 UTC head sample). Author: research agent. Status: **PASS** (measurement done; both external claims verified, with nuances below).

The PULLED program counts windows in **slots**, never wall-clock. The UI only shows an estimate in seconds. This gate measures how many milliseconds a slot really takes on mainnet so the UI conversion and the `window_slots` / `vrf_timeout_slots` constants are grounded in data instead of the nominal number.

---

## 1. Method

**Script:** `research/scripts/g6-slot-time.mjs` (Node 24, no dependencies, `fetch` only).

**Endpoints:** `https://api.mainnet-beta.solana.com` (primary; all 137 calls were served by it), with `https://solana-rpc.publicnode.com` and `https://solana.drpc.org` as fallbacks (rotation after 3 consecutive 429s — never triggered).

**Procedure:**
1. `getSlot` (commitment `finalized`) → head slot, then `getBlockTime(head)`.
2. Calibration: assume 400 ms/slot, probe `getBlockTime` ~30 days back, compute the real average rate, re-probe at `head − 30 d / rate`. Because the 30-day window straddles a protocol change (see §3), the calibrated tail landed at 2026-09-20 23:18 UTC, i.e. the window actually spans **32.55 days** (slightly more than 30; nothing was dropped).
3. 121 target slots evenly spaced between tail and head (120 intervals, one every ~96,375 slots ≈ 6.5 h). For each target, `getBlockTime(target)`; if the RPC answers "slot skipped / block not available" (`-32004/-32007/-32009`), probe `target+1, target−1, target+2, …` up to ±32. In this run **no target slot was skipped** (`probe_offset = 0` for all 121 samples).
4. Rate limiting: fixed 220 ms pacing between calls; HTTP 429 → exponential backoff (1 s, 2 s, 4 s … capped 60 s, honouring `Retry-After`). 14 backoffs occurred, 0 other errors.
5. ms/slot per interval = `(blockTime[i] − blockTime[i−1]) × 1000 / (slot[i] − slot[i−1])`. Daily figure = slot-weighted mean of the intervals whose start sample falls on that UTC day. Overall = `(t_last − t_first) / (slot_last − slot_first)`.

`getBlockTime` returns the validator-reported Unix timestamp (second resolution, stake-weighted median). Each interval spans ≥ 96k slots (≥ 5.7 h) so the 1-second quantisation error is < 0.01 ms/slot. **Skipped slots are included** in ms/slot — this is the number the UI needs (how long `N` slot numbers take to pass), not the block-production time of produced blocks.

**Cross-checks run on 2026-10-23 ~12:30 UTC** (`research/data/G6-rpc-probe.txt`):
- `getEpochInfo` → epoch **1065**, `slotsInEpoch` 432,000, absolute slot 460,443,072.
- `getVersion` → `solana-core 4.3.2`.
- `getRecentPerformanceSamples(10)` → 282–289 slots per 60 s sample = **207.6–212.8 ms/slot** over the last 10 minutes.
- `getAgGenesisCert` → non-null certificate for block slot **459,652,999** (see §4, Alpenglow).

## 4. External claims checked

### Claim A — "slot time became 200 ms in October 2026"

**VERIFIED as the nominal target; measured reality is ~216 ms.**

- Solana Foundation upgrade page "Reduced Slot Times" lists the four SIMD-0525 steps with feature-gate keys: 350 ms (epoch 1020, slot 440,640,000, 2026-08-21), 300 ms (epoch 1024, slot 442,368,000, 2026-08-28), 250 ms (epoch 1037, slot 447,984,000, 2026-09-18), **200 ms (epoch 1053, slot 454,896,000, 2026-10-09 ~14:35 UTC) — "Live on Mainnet"**. It also states epochs are now ~24 h and blockhash expiry (150 blocks) is ~30 s. https://solana.com/upgrades/reduced-slot-times
- SIMD-0525 "Reduce Slot Times": https://simd.live/simd/0525-reduce-slot-times ; Agave PR: https://github.com/anza-xyz/agave/pull/12264/
- Solana Compass, 2026-10-09 15:25 UTC: Anza confirmed the 200 ms step at 14:42 UTC, epoch 1053; last measured epoch at the 250 ms stage averaged 268.5 ms; Compass expected 215–219 ms if the earlier overshoot carried over. https://solanacompass.com/news/solanas-200ms-slot-time-is-live-on-mainnet-at-epoch-1053-completing-simd-0525
- Solana Compass, 2026-09-18 (250 ms step, epoch 1037, 05:06 UTC): https://solanacompass.com/news/solana-activates-250ms-slot-time-at-epoch-1037-fourth-step-of-simd-0525
- Our data agrees on both the date (step visible on 2026-10-09) and the overshoot (267.6 ms at the 250 ms target; 216.6 ms at the 200 ms target).
- Note: the Agave feature-gate wiki (edited 2026-10-22) no longer lists SIMD-0525 under "Pending", consistent with it being fully activated: https://github.com/anza-xyz/agave/wiki/Feature-Gate-Tracker-Schedule

### Claim B — "Alpenglow is active on mainnet since 21 October 2026"

**VERIFIED (Votor only), independently confirmed by our own RPC probe.**

- Solana Foundation: Alpenglow (SIMD-0326 "Alpenglow Consensus Protocol") "activated in epoch 1064, which started on Wednesday, October 21, 2026, at approximately 13:36 UTC"; Votor "shipped in Agave 4.3 and has been live on mainnet since epoch 1064"; genesis block slot 459,652,999, Alpenglow consensus from slot 459,653,000; required client v4.3.2 (Agave / Jito-Solana / Harmonic Salsa; Firedancer and Frankendancer not supported for the migration). **Rotor "is planned for a later release … and is not yet scheduled."** Devnet activation: epoch 1167, 2026-09-25 19:30 UTC. https://solana.com/upgrades/alpenglow

- Other coverage (secondary): https://www.crowdfundinsider.com/2026/10/319911-anza-activates-alpenglow-on-solana-sol-mainnet-slashing-finality-to-150-milliseconds/ , https://decrypt.co/380974/solana-alpenglow-upgrade-date , https://www.bankless.com/read/news/alpenglow-is-coming-to-solana-mainnet-next-week.md

**Caveats that matter for PULLED:**

## 5. Conversion to use in the UI

> **1 slot ≈ 217 ms** (measured 2026-10-10 → 2026-10-23, 55 intervals / 5.30 M slots, daily range 211.7–218.7 ms, i.e. **±4 ms ≈ ±2 %** around 215). Nominal protocol target: 200 ms. Early post-Alpenglow reading (2026-10-21 → 23): ~212 ms.

Recommended implementation:
- Constant for display: `MS_PER_SLOT_EST = 215` (midpoint of the 200 ms-regime daily range; errs < 2 % either way). Always render with "≈".
- Optional live calibration: call `getRecentPerformanceSamples(10)` and compute `Σ samplePeriodSecs×1000 / Σ numSlots`; clamp to [190, 280] and fall back to 215. This costs one RPC call and tracks drift (e.g. if the post-Alpenglow ~212 ms persists, or if a future SIMD lowers the target again).
- Do **not** use 243 ms (the raw 30-day mean) — it is an artefact of the 9 Oct regime change. Do not use 400 ms (pre-August 2026 folklore).
- Re-run this gate after any Agave major release or SIMD affecting slot timing (watch https://solana.com/upgrades and the Agave feature-gate wiki).

## 6. Recommended `window_slots`

Computed with the measured 216.5 ms (realised seconds shown), with nominal-200 ms equivalents for comparison.

| Target duration | **window_slots (recommended)** | Realised at 216.5 ms | At 212 ms (post-Alpenglow early) | If nominal 200 ms were exact |
|---|---|---|---|---|
| 10 s | **46** | 9.96 s | 9.75 s | 9.2 s (nominal pick would be 50) |
| **~20 s** | **92** | **19.9 s** | 19.5 s | 18.4 s (nominal pick would be 100) |
| 30 s | **139** | 30.1 s | 29.5 s | 27.8 s (nominal pick would be 150) |

Rationale: users experience wall-clock, so size windows from the measured rate, not the nominal one. If the product owner prefers round numbers tied to the protocol target, 50 / 100 / 150 slots currently realise ≈ 10.8 / 21.7 / 32.5 s. Whichever is chosen, keep `window_slots` as a program parameter (not a hard-coded constant) so it can be retuned without redeploying when slot time moves again.

## 7. `vrf_timeout_slots` suggestion (final value depends on G2)

A timeout expressed in slots is *shorter* in wall-clock when slots are faster, so convert a time budget with the **lowest** observed ms/slot (211.5 ms) to be conservative:

`vrf_timeout_slots = ceil( (VRF_latency_p99_s + margin_s) / 0.2115 )`

with `margin_s` ≥ 2 s (covers one leader rotation of 4 slots plus RPC/relayer jitter). Examples, to be filled from G2's measured VRF p99:

| G2 VRF p99 | margin | vrf_timeout_slots | wall-clock at 216.5 ms |
|---|---|---|---|
| 2 s | 2 s | 19 | 4.1 s |
| 3 s | 2 s | 24 | 5.2 s |
| 5 s | 2 s | 34 | 7.4 s |
| 10 s | 2 s | 57 | 12.3 s |

Floor recommendation: never below 20 slots (≈ 4.3 s). If G2 finds the VRF provider waits for `finalized` commitment, note that Alpenglow's finality target (150 ms, UNVERIFIED on mainnet) may cut its latency materially compared with the pre-21-Oct ~12.8 s TowerBFT finality — G2 should measure after 2026-10-21, not reuse older numbers.

## 8. Verdict

**PASS.**
- Measurement completed on mainnet with 121 samples / 120 intervals, raw data saved, method reproducible.
- Current slot time: **≈ 217 ms** (200 ms-target regime since 2026-10-09; ±2 % day-to-day), trending ~212 ms in the first two days after Alpenglow (early).
- Claim "200 ms slots in October 2026": **VERIFIED** as target (2026-10-09, epoch 1053); realised ≈ 216–218 ms.
- Claim "Alpenglow active since 2026-10-21": **VERIFIED** (Votor; epoch 1064; handoff slot 459,653,000; confirmed by `getAgGenesisCert`). Rotor not scheduled; 150 ms finality **UNVERIFIED** as a measurement.

# G2 — Randomness source for PULLED (ORAO VRF vs Switchboard On-Demand)

Date: 2026-10-23. Author: research agent (no Solana CLI available on this machine; all on-chain facts come from public JSON-RPC reads done by the scripts in `research/scripts/`, raw outputs in `research/data/`).

Requirement recap: a window counted in slots; at close, ONE seed that no participant, window creator, keeper or slot leader can influence or predict; requested strictly after the window is sealed; delivered in a later slot; refund everybody if nothing arrives after `vrf_timeout_slots`; target loop ≈ 20 s per window.

## 0. Headline

1. **Switchboard is out.** Switchboard announced on 2026-09-19 that "all implementations are deprecated effective immediately" with "all support services ending on September 25" ([solanacompass news, 2026-09-19](https://solanacompass.com/news/switchboard-oracle-protocol-shuts-down-giving-solana-defi-six-days-to-migrate)); QuickNode's Switchboard randomness guide now carries the banner "As of September 25, 2026, Switchboard has shut down and its oracle services are no longer available" ([QuickNode guide](https://www.quicknode.com/guides/solana-development/3rd-party-integrations/generate-onchain-random-numbers-with-switchboard-vrf)). On-chain confirmation: the newest 60 mainnet transactions touching `SBondMDrcV3K4kxZR1HNVT7osZxAHVHgYXL5Ze1oMUv` (as of 2026-10-23, newest 2026-10-15T23:59 UTC) are exclusively `RandomnessClose` / `RandomnessCloseLut` rent-reclaims — no commit, no reveal (`data/sb-recent-activity.json`). The docs site `docs.switchboard.xyz` no longer resolves (DNS `ENOTFOUND` from two independent fetchers). Its design is still analysed below because the question asked for it and because its weaknesses are instructive, and its historical commit→reveal latency was measured for completeness.
2. **ORAO VRF works and is the recommendation**, but its *usable* latency (3-of-3 node quorum) is bimodal: **median 20 slots / 4 s, p90 340 slots / 72 s, p99 528 slots / 113 s, max 726 slots / 158 s** (n = 313 mainnet requests, 2026-10-16/17). 76 % of requests are usable within 20 s; 24 % are not.
3. Therefore **a strictly sequential 20 s loop is not tenable**. Either pipeline windows (open the next window on a fixed slot schedule while previous windows settle asynchronously — then the 20 s cadence survives and only settlement lags), or, if the loop must be sequential, size the loop at ≈ p99: **≥ 540 slots (~2 min) per window with `vrf_timeout_slots` ≈ 900**. Details in §9.
4. Transaction V1 (4096 B) **is live on mainnet** (feature `txv1aq4pp281K9um3tnPgkfX8UqtFT6wcVW3hNezGLL` activated at slot 447,120,000, epoch 1035, 2026-09-15; verified by reading the feature account — `data/txv1-feature-status.json`). 35 of 314 sampled ORAO request transactions were already v1. It changes nothing material for either flow (§8).

## 3. Flows

### 3.1 ORAO classic VRF

Instructions and accounts come from the IDL ([js/src/types/orao_vrf.json](https://github.com/orao-network/solana-vrf/blob/master/js/src/types/orao_vrf.json), program version 0.6.1) and the SDK ([rust/sdk/src/lib.rs](https://github.com/orao-network/solana-vrf/blob/master/rust/sdk/src/lib.rs), [rust/sdk/src/sdk/mod.rs](https://github.com/orao-network/solana-vrf/blob/master/rust/sdk/src/sdk/mod.rs)).

1. **Request** — `request_v2(seed: [u8;32])`, accounts `payer (mut, signer)`, `network_state (mut, PDA ["orao-vrf-network-configuration"])`, `treasury (mut, must equal network_state.config.treasury)`, `request (mut, PDA ["orao-vrf-randomness-request", seed], init, 8 + 741 bytes)`, `system_program`. Payer pays `request_fee` (500,000 lamports) to the treasury and 4,455,160 lamports rent. Usually called by CPI from the consumer program (297 of 314 sampled requests were CPIs). Errors: `ZeroSeed`, `SeedAlreadyInUse` ("Another account is using the provided seed, so randomness can be predicted"), `InsufficientFunds`, `UnknownTreasuryGiven`. Emits `Request { seed, client, paid_with_spl }`.
2. **Fulfil** — each ORAO node sends its own transaction `[Ed25519SigVerify(seed signed by node key), fulfill_v2]` with accounts `payer (node, signer)`, `instruction_acc (Sysvar1nstructions…)`, `network_state`, `request`, `client (mut, == request.client)`, `system_program`. The SDK builds it as `ed25519_instruction::new_ed25519_instruction(&fulfill_authority, &self.seed)` placed "right before the second instruction (the Fulfill instruction)". The program reads the sysvar (`MissingEd25519SigVerifyInstruction`), checks the signed message is the seed (`InvalidFulfillMessage`) and that the pubkey is in `fulfillment_authorities` (`UnauthorizedFulfillmentAuthority`), appends `RandomnessResponse { pubkey, randomness: sig64 }` and emits `Response`. When `quorum(responses, authorities)` holds it XORs the responses into `randomness: [u8;64]`, converts the account to `Fulfilled`, reallocs it to 137 bytes, refunds the rent difference (3,108,960 lamports) to `client`, and emits `Fulfill { seed, randomness }`. Verified on mainnet tx `VYDWJkwb9PSWwky9Cd3pUyWc7QqcVnh2TtnH5s4Gn1pu1F2BvaScJ1Hn713AAWYJwYU7U27iAWutxk6JJV3vdwT` (`data/orao-fulfill-rent-check.json`): request account 4,455,160 → 1,346,200 lamports, client +3,108,960, data now 137 bytes starting `8befb8d7e356bfe2 01`. In 307 of 313 sampled requests the `Fulfill` event is in the **third** fulfill tx (6 cases "second" are same-slot ordering artefacts), confirming quorum = 3 of 3.
3. **Consume** — the consumer reads the PDA with `RandomnessAccountData::try_deserialize` and `fulfilled_randomness() -> Option<&[u8;64]>` ([state/mod.rs](https://github.com/orao-network/solana-vrf/blob/master/rust/sdk/src/state/mod.rs), [randomness_v2.rs](https://github.com/orao-network/solana-vrf/blob/master/rust/sdk/src/state/randomness_v2.rs)). ORAO's own CPI example does exactly this in `state.rs::current_state`.

Who pays: requester pays fee + rent (rent mostly refunded); nodes pay their own fulfil transactions (10,000 lamports each observed — two signatures: node + … actually 1 signature + priority; see `data/orao-raw-analysis.json`).

### 3.2 Switchboard On-Demand randomness (historical)

Sources: crate `switchboard-on-demand` 0.13.0 source [`on_demand/accounts/randomness.rs`](https://docs.rs/crate/switchboard-on-demand/0.13.0/source/src/on_demand/accounts/randomness.rs), TS SDK [`src/accounts/randomness.ts`](https://github.com/switchboard-xyz/on-demand/blob/main/src/accounts/randomness.ts) and [`src/oracle-interfaces/gateway.ts`](https://github.com/switchboard-xyz/on-demand/blob/main/src/oracle-interfaces/gateway.ts), example [`sb-on-demand-examples/solana/randomness/coin-flip`](https://github.com/switchboard-xyz/sb-on-demand-examples/tree/main/solana/randomness/coin-flip).

1. **Create** — `Randomness.create(program, keypair, queue)`: a 480-byte `RandomnessAccountData` (fields `authority, queue, seed_slothash[32], seed_slot, oracle, reveal_slot, value[32]`, discriminator `[10,66,229,135,220,239,217,114]`), plus a reward escrow ATA and an address lookup table; payer = provider wallet.
2. **Commit** — `randomness_commit`, accounts `randomness, queue, oracle, recent_slothashes (SlotHashes sysvar), authority (signer)`. The program stores the hash of the previous slot: the example asserts `randomness_data.seed_slot != clock.slot - 1 → RandomnessExpired` in the consumer instruction bundled in the same tx. The oracle is picked client-side (`fetchFreshOracle`).
3. **Reveal** — the *client* waits (SDK sleeps 3 s), HTTP-POSTs `/gateway/api/v1/randomness_reveal` with `{slothash, randomness_key, slot, rpc}` to the chosen oracle's gateway, receives `{signature, recovery_id, value}` ("Signature of the randomness using the oracle's enclave key"), and sends `randomness_reveal(signature, recovery_id, value)` with 13 accounts (`randomness, oracle, queue, stats, authority, payer, recent_slothashes, system_program, reward_escrow, token_program, associated_token_program, wrapped_sol_mint, program_state`). The program verifies the secp256k1 signature against the oracle's attested enclave key and sets `reveal_slot = clock.slot`, `value`.
4. **Consume** — `get_value(clock_slot)` returns `SwitchboardRandomnessTooOld` unless `clock_slot == reveal_slot`, so reveal and consume **must be in the same transaction** — i.e. the consumer builds the transaction already knowing the value.

Who pays: the consumer pays rent, commit, and reveal (plus the oracle reward escrow); the oracle pays nothing on-chain.

## 4. Attack surfaces

### 4.1 Seed choice (ORAO)

- The seed is a 32-byte argument chosen by the requester and must be unique forever (`SeedAlreadyInUse`). The value is `XOR_i Ed25519(sk_i, seed)`. Ed25519 (RFC 8032) is **deterministic**: given the seed and the three node keys the value is fixed at request time — in fact fixed as soon as the seed is known.
- **Deterministic seed such as a PDA key**: safe against everyone *except* the node operator. A PDA-only seed is knowable long before the window closes, so the operator (or anyone who obtained the 3 keys) could compute the outcome of a future window and enter it. Nobody else can: computing the value requires the private keys. Mitigation adopted (§7 and the integration notes): `seed = sha256(domain || window_pda || close_slot || entries_count || entries_commitment)` where `entries_commitment` is a running hash of all entries — it is unknown to everyone, including ORAO, until the last entry has landed, and entries after `close_slot` are rejected, so the operator learns the seed only once the window is already sealed.
- **Requester grinding seeds**: useless on its own (no private keys). The real "grinding" risk is a *keeper* that creates several requests and binds the one it likes: killed by deriving the seed on-chain from window state and taking no seed argument, so a window maps to exactly one PDA and one request (`SeedAlreadyInUse` even prevents re-requesting).
- **Participants grinding entries** to steer `entries_commitment`: pointless without the node keys; with the node keys it is the collusion case below.

### 4.2 Fulfiller trust (ORAO)

- 3 authorities on mainnet, quorum 3-of-3 (`majority(3) = 3*2/3+1 = 3`); any single node outage halts fulfilment — this is visible in the data as the latency tail (node `A9iZ…` is the slowest in 164 of 313 requests, p90 70 s).
- Signatures are deterministic, so a node **cannot choose** its contribution; the only levers are (a) *withholding* after computing the value (free option: void rounds it dislikes, not pick winners — bounded by the timeout/refund), (b) *collusion of all three keys* to precompute outcomes (needs the seed → defeated before seal by `entries_commitment`, but after seal the operator still knows the result ~immediately and could in principle front-run the `settle` tx only if the settle had any user-controlled choice — it does not).
- Operational centralisation: the config authority, treasury, fulfiller #1 and the **program upgrade authority** are the same key `9ZTH…`; the program is upgradeable and closed source. That is the residual trust assumption ("Proof of Authority" per ORAO's own table). Keep the timeout/refund path and monitor unfulfilled requests on-chain.
- Fulfil is effectively permissionless at the transaction level (anyone could submit a valid `[Ed25519, fulfill_v2]` pair) but only the key holders can produce the signatures.

### 4.3 Slothash and TEE (Switchboard)

- Seed = hash of slot `commit_slot - 1`. The leader of that slot produces the hash and can grind block contents, but to *bias* it would need to evaluate the oracle's keyed function on candidate hashes before publishing the block; the gateway only serves reveals for committed accounts (**UNVERIFIED**, docs unreachable). The leader of the commit slot itself can only censor/delay the commit (then the consumer's `seed_slot == clock.slot - 1` check fails and the round is retried).
- Single oracle per request, trust = SGX attestation + Switchboard's key management; no quorum.
- Reveal deadline: the crate exposes only `is_revealable = seed_slot < clock_slot`; no on-chain expiry constant was found in the crate or TS SDK; the SlotHashes sysvar keeps 512 slots, so a reveal is possible as long as the oracle can still verify the slothash (third-party audits talk about a "64-slot commit window" at the application level — [issue](https://github.com/sebastianmontero/premium-bonds/issues/10), not fetchable, **UNVERIFIED**).
- **Free option by construction**: the consumer fetches the value over HTTP before sending the reveal, and `get_value` is only valid in the reveal slot. The only protection is "anyone can reveal" plus economic design, which is exactly what PULLED cannot rely on (a keeper that is also a participant would void losing rounds). This alone would have disqualified Switchboard even if it were alive.

### 4.4 The abort / free-option problem — how the program must be structured (both providers)

1. The seed must be **bound before** anybody knows anything: derived on-chain from sealed state, stored in the window, one request per window (PDA uniqueness).
2. The value must be **written on-chain by the provider**, not by any PULLED actor (true for ORAO; false for Switchboard).
3. `settle` is **permissionless** and has no inputs besides the window and the randomness account.
4. `refund_window` is permissionless but opens **only** when `clock.slot > requested_at_slot + vrf_timeout_slots` **and** `fulfilled_randomness().is_none()`; once a value exists the refund path is closed forever. A race between a late fulfil and a refund is harmless because no PULLED actor knows the value before it is on-chain.
5. Refunds return exactly `entry.lamports` to `entry.owner`; no fee is kept, so forcing a refund has no payoff beyond denial of service.
6. Entries after `close_slot` are rejected and `seal_and_request` requires `clock.slot > close_slot`, so no participant action can depend on the value.

## 7. Timeout and refund path (what the program sees, how it is proven)

What the program sees when ORAO never answers: the randomness PDA exists, is owned by ORAO, holds 4,455,160 lamports, 749 bytes, discriminator `8befb8d7e356bfe2`, enum tag `00` (Pending), `responses.len() ∈ {0,1,2}`; `RandomnessAccountData::fulfilled_randomness()` returns `None`. Nothing else changes; there is no error, no event, no deadline inside ORAO — the deadline is entirely PULLED's `vrf_timeout_slots`.

Test ("provider never answers"), runnable on `solana-test-validator --clone VRFz… --clone 91JpgS1vZUPczygkLgNQQL7tzAWUvc7M7HHVEzi8LoPV --clone 5ER1oENnV4srxYdAynUfRzWeQCPQaqMiAp4VqyMbSqnK` (program, programdata, network state) where nobody fulfils, or on LiteSVM/Bankrun with the same accounts loaded:

```
given  window W open, N entries e_i with lamports L_i from distinct wallets, vault balance = Σ L_i + fee + rent
when   warp to close_slot + 1; keeper calls seal_and_request(W)            -> W.state == Sealed, W.vrf_request == PDA(seed(W))
       assert randomness PDA pending (tag 00), vault -= 500_000 + 4_455_160
when   warp to requested_at_slot + vrf_timeout_slots (exactly)             -> refund_window(W) by random wallet X fails TimeoutNotReached
when   warp to requested_at_slot + vrf_timeout_slots + 1
       refund_window(W) signed by random wallet X (no authority)          -> ok, W.state == Refunding
       for each i: refund_entry(W, i) by wallet X                          -> wallet(e_i).lamports == before_i + L_i  (exact, no fee kept)
       assert vault.lamports == 0 (or == rent-exempt minimum if kept), W.state == Refunded
       assert settle(W) now fails BadState
then   (late fulfil) overwrite PDA with a Fulfilled image                   -> settle(W) still fails BadState; refund cannot be re-run (idempotent)
```

And the mirror test ("fulfil arrives before timeout"): write the fulfilled image (`8befb8d7e356bfe2 01 | client | seed | 64 bytes`) before the deadline → `refund_window` fails `AlreadyFulfilledUseSettle`, `settle` by anyone succeeds, winner == off-chain computation from the same 64 bytes.

Budget: with the measured distribution, `vrf_timeout_slots = 900` (~3–4 min) would have refunded 0 of 313 sampled windows; `600` would have refunded 1 (0.3 %); `300` would have refunded 13 % — far too many.

## 8. Transaction V1 note

- Status: **live on mainnet**. The feature account `txv1aq4pp281K9um3tnPgkfX8UqtFT6wcVW3hNezGLL` is owned by `Feature111…` with data `01 8082a61a00000000` ⇒ activated at slot 447,120,000 (epoch 1035; the [Solana upgrade page](https://solana.com/upgrades/larger-transaction-sizes) says 2026-09-15 ~01:00 UTC), current slot 460,443,072 at check time. SIMD-0296 (size 1232 → 4096 bytes) delivered via SIMD-0385 (v1 format): up to 64 inline accounts, **no address-lookup tables in v1**, compute budget set in the transaction header (ComputeBudget instructions are no-ops), base58 RPC encoding capped at 1232 B so >1232 B needs `encoding: base64`, `getTransaction` needs `maxSupportedTransactionVersion: 1` (our first run failed with `-32015` on exactly this), Jito/Agave ≥ 4.2.2 for leaders.
- Already in the wild: 35 of 314 sampled ORAO request transactions (from consumer programs) were v1; all 941 ORAO fulfil transactions were legacy.
- Effect on ORAO: none on latency or trust. Each node's fulfil tx is tiny (Ed25519 ix ≈ 16 + 64 + 32 + 32 bytes + `fulfill_v2` with 6 accounts). V1 would let **one** submitter bundle all three `[Ed25519, fulfill_v2]` pairs in a single transaction (the Ed25519 precompile does not need the key as a tx signer), i.e. "fit the full proof in one atomic transaction" — but that only helps if the three nodes hand their signatures to a common relayer, which is ORAO's architecture decision, not ours, and the quorum tail is a *node* delay, not a packing problem. For PULLED, `seal_and_request` and `settle` fit comfortably in legacy size; v1 is useful only if `settle` wants to pay out many winners in one tx (64 inline accounts).
- Effect on Switchboard: v1 would have removed the size pressure of the 13-account reveal + consume bundle and the SDK's lookup-table dance, but it does not touch the free-option flaw (the client still learns the value before sending). Moot now.

## 9. Recommendation

**Provider: ORAO VRF classic (`request_v2`/`fulfill_v2`)**, seed derived on-chain as in §4.1, vault PDA as payer. Switchboard is dead; the Callback VRF variant of ORAO adds operational constraints (upgrade-authority registration, funded client PDA, callback deadline, "callback should never fail") without changing the trust model and is kept in reserve only.

**Window length / loop.** The measured *usable* latency is median 4 s but p90 72 s and p99 113 s (528 slots), bimodal because quorum is 3-of-3 and one node is slow about a quarter of the time. Consequences:

1. **A sequential 20 s loop (window N+1 opens only after window N settles) is NOT tenable.** 24 % of windows would wait longer than the whole loop; the loop would stall for 1–2 minutes several times per hour.
2. **Shortest tenable sequential window:** the window plus settlement must cover ≈ p99 ⇒ **≥ 540 slots (~2 min at 0.217–0.25 s/slot)** of settlement wait after close, i.e. a ~2-minute cadence, with `vrf_timeout_slots = 900` (p99 × 1.7, zero refunds in the sample). A 60 s cadence would still break 13 % of the time.
3. **Recommended design: pipelined windows.** Open windows on a fixed slot grid (e.g. every 80–100 slots ≈ 20 s) regardless of whether earlier windows have settled; each window has its own PDA, seed, request and timeout; `settle` and `refund_window` are permissionless and asynchronous. The 20 s *entry* cadence is preserved; settlement of a given window lands 4 s later in the typical case and up to ~2 min later in the tail; funds of at most ~6 concurrent windows are in flight. This is the only way to keep the 20 s loop with a 3-of-3 PoA VRF.
4. Keep `close_slot` strictly before the request, bind the seed at seal, and set `vrf_timeout_slots` to 900 initially; re-measure with `scripts/measure-orao.js` monthly (the per-node tail is operational and may change).

## 10. Bias test designs (against the chosen ORAO flow)

Each test states what the attacker controls, what they try, and the assertion proving failure. "Oracle" = a test double that writes a fulfilled image into the randomness PDA (LiteSVM `set_account`) using a fixed secret function `F(seed) = sha512(k || seed)` standing in for `XOR_i Ed25519(sk_i, seed)`; the tests never give the program a value chosen *after* observing the seed except where the attacker is explicitly ORAO.

**T1 — Participant.** Controls: its own entries (count, timing, lamports, pubkeys), any number of wallets, order of its transactions, and it may read everything on-chain. Tries: (a) enter after `close_slot`; (b) grind entries so that `seed(W)` lands on a value whose `F(seed)` favours it — it can compute `seed(W)` for every candidate entry set but **not** `F` (no key); (c) enter in the same slot as `seal_and_request`; (d) call `settle`/`refund_window` itself. Assertions: (a) `enter` fails `WindowClosed` for any slot > `close_slot`; (b) over 10,000 simulated windows where the participant picks, among 16 candidate final entries, the one whose seed hashes "best" under a *wrong* key `k'`, the win rate under the true `F_k` is within 3σ of its stake share (binomial test) — i.e. seed-grinding without the key is indistinguishable from random; (c) the entry landing in `seal_and_request`'s slot is either before (included, affects seed) or after (rejected) — in both orders `W.vrf_seed` equals the recomputation from the entry set actually stored, and the request PDA matches `W.vrf_seed`; (d) `settle` by the participant yields the same winner as `settle` by anyone else (pure function), `refund_window` before timeout fails, and after timeout the participant gets back exactly `L_i`, never more.

**T2 — Window creator.** Controls: window parameters at creation (`close_slot`, limits, `vrf_timeout_slots` within bounds), may also be a participant, may call any permissionless instruction. Tries: (a) pass a seed or a randomness account of its choice; (b) create two windows that map to the same seed; (c) seal before `close_slot`; (d) re-seal with a different seed; (e) set a tiny `vrf_timeout_slots` to force refunds when it dislikes the (still unknown) outcome. Assertions: (a) `seal_and_request` has no seed argument and `random` must equal `PDA(seed(W))` (`WrongRandomnessAccount` otherwise); (b) seeds differ because `window.key()` is part of the hash — property test over 10,000 random windows: no collision, and `SeedAlreadyInUse` is unreachable; (c) `WindowStillOpen`; (d) second call fails `BadState` (and ORAO would fail `SeedAlreadyInUse`); (e) `vrf_timeout_slots` is clamped to `[MIN_TIMEOUT = 600, MAX_TIMEOUT]` at creation, and refund is impossible once a value exists regardless of timeout.

**T3 — Keeper / caller.** Controls: when (and whether) to send `seal_and_request`, `settle`, `refund_window`; may be a participant; sees the fulfilled value on-chain before anyone acts. Tries: (a) delay `seal_and_request` until a favourable moment — but the seed depends only on sealed state, not on when the request is sent; (b) send several requests and choose; (c) see an unfavourable value and call `refund_window` instead of `settle`; (d) withhold `settle` forever. Assertions: (a) for the same sealed state, `seal_and_request` at `close_slot+1` and at `close_slot+10_000` produce identical `W.vrf_seed` and PDA; (b) only one PDA per window can exist (`SeedAlreadyInUse`/`BadState`); (c) with a fulfilled image present, `refund_window` fails `AlreadyFulfilledUseSettle` at every slot, including `> requested_at_slot + vrf_timeout_slots`; (d) `settle` by an unrelated wallet succeeds with the same winner; liveness is permissionless.

**T4 — Slot leader.** Controls: ordering, inclusion and timing of transactions in its slot(s); the block hash of its slot; may collude with a participant. Tries: (a) reorder entries and the seal tx within its slot; (b) censor the seal/settle/refund tx; (c) grind its block so that the seal lands in a chosen slot or the fulfil lands in a chosen slot; (d) include the fulfil and a refund in the same slot. Assertions: (a) any ordering yields a consistent `(entries, seed)` pair — the winner is a function of the stored entry set and `F(seed)`, never of slot number or block hash (property test: identical entry set across 100 random orderings ⇒ identical winner; the seed excludes the seal slot and all hashes); (b) censorship only delays — after the leader's slots, anyone's tx succeeds; the request timestamp (`requested_at_slot`) only moves the timeout later, never changes the seed; (c) `fulfill` is written by ORAO with signatures over the seed only — no slot or blockhash enters the value; (d) if the fulfil executes first, the refund fails `AlreadyFulfilledUseSettle`; if the refund executes first (only possible past the timeout), the late fulfil is ignored (`settle` fails `BadState`) and everyone is refunded — in neither order does the leader learn the value before it is public, so the leader's choice cannot be conditioned on it (assert the refund-first branch is reachable only when `slot > requested_at_slot + vrf_timeout_slots`).
